URLs are a host concern. A pack is addressed by **page id** (`blog.post`), not
by `/p/{slug}`. That is what makes a UI swappable: your app pack and a
third-party theme can both implement `blog.post` while the Ktor route stays
put. It is also what makes a one-pack app simple — the registry is the only
router.

`PageRegistry` stores the id, a Ktor-style pattern, and the payload
serializer. Duplicate ids throw. Unknown ids throw. Matching supports
`{param}` segments.

The registry plus those serializers **is** the page contract. See
<a href={path("/docs/core-concepts/contracts")}>Page contracts</a>.

## Visit vs document

A first load is a document request. The host returns the HTML shell, the seed
node (`#__keel_seed`), `seed.head` in the real `<head>`, and a module URL.
That document GET is the **SEO unit** — crawlers and share bots never send
`X-Keel-Visit`. See
<a href={path("/docs/core-concepts/head")}>Document head and SEO</a>.

Client navigation is a **visit**: `GET`/`POST` the **page URL** with
`X-Keel-Visit: true` and `Accept: application/json`. The response is the same
seed JSON.

Non-GET visits send form or JSON bodies on that same path. `422` is still a
seed — with `errors`. Typed JSON **writes** that are not a page go through
<a href={path("/docs/core-concepts/actions")}>server actions</a>
(`POST /__keel/action/{id}`). `/__keel/navigate?to=` remains a thin
compatibility proxy for the pages DSL; custom trees do not need it.

## respondPage

`respondPage` is the primitive. Any Ktor route can return a Keel page. The
pages DSL is sugar: register path + loader, then on match call `respondPage`.

<CodeBlock
  lang="kotlin"
  bw="ktor"
  title="Pages DSL"
  code={`fun Application.harbor(bundle: FrontendBundle) {
    keel {
        this.bundle = bundle
        title = "Harbor"
        notFoundPageId = "harbor.notFound"
        pages {
            page<HomePage>("harbor.home", "/") { HomePage(...) }
            page<UserPage>("harbor.user", "/u/{id}") { ... }
        }
    }
}`}
/>

<CodeBlock
  lang="kotlin"
  bw="ktor"
  title="Custom tree"
  code={`routing {
    route("/shop") {
        keel(shopBundle) {
            get("/{id}") {
                val item = load(call.parameters.getOrFail("id"))
                call.respondPage("shop.item", ShopItemPage(item), params = mapOf("id" to item.id))
            }
        }
    }
}`}
/>

`Route.keel` registers the bundle for asset serving and sets a default so
`respondPage(pageId, data)` can omit the bundle argument. It does not steal
unmatched paths. The `{path...}` not-found catch-all stays on the
application-level pages DSL only.

## History

Successful visits `pushState` the seed. Back/forward re-applies the stored seed
without a network round-trip unless the entry module changed.

`replace` swaps the current history entry (login, pack switch). `preserveState`
on the same page id calls `update()` instead of remounting.

## Why packs must not own paths

If a theme hard-codes `/p/{slug}`, you cannot swap it for a pack that uses the
same id on a different host path. The id is the contract. The path is
decoration the host is free to restyle — or version.
